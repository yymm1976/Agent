### C1: 串行模式跳过 PolicyEngine 安全检查

**文件**: [loop.ts](file:///c:/Users/杨铭/Desktop/Agent/routedev/src/agent/loop.ts#L928-L982)（并行模式）vs [loop.ts](file:///c:/Users/杨铭/Desktop/Agent/routedev/src/agent/loop.ts#L1165-L1201)（串行模式）

**严重性**: Critical — 安全漏洞

**验证结果**: 已确认 ✅

**描述**: ReAct 循环的并行模式在 L945-960 调用 `this.policyEngine.evaluateAction()` 进行策略引擎检查，串行模式（L1165-1201）只有中间件检查，完全没有策略引擎调用。这意味着串行模式下策略引擎的 fail-closed 安全检查被完全绕过——任何被策略引擎拒绝的工具调用在串行模式下都会被放行。

**并行模式（正确）**:
```typescript
// L945-960: 策略引擎检查
if (!mwCtx.metadata.permissionDenied && this.policyEngine) {
  const policyDecision = this.policyEngine.evaluateAction({
    toolName: toolCall.name,
    description: toolCall.name,
    args: toolCall.arguments,
  });
  if (policyDecision.denied) {
    mwCtx.metadata.permissionDenied = policyDecision.reason ?? '策略引擎拒绝';
  }
}
```

**串行模式（缺失）**: L1165-1201 仅有中间件检查，无上述策略引擎代码块。

**修复建议**: 在串行模式的中间件检查（L1201）之后、工具执行之前，插入与并行模式 L945-960 相同的策略引擎检查代码。

### C2: completion-gate runTests 命令注入（Windows）

**文件**: [completion-gate.ts](file:///c:/Users/杨铭/Desktop/Agent/routedev/src/agent/completion-gate.ts#L267-L280)

**严重性**: Critical — 安全漏洞

**验证结果**: 已确认（仅 runTests 方法）⚠️

**描述**: `runTests` 方法将 `files` 数组直接展开为命令参数，在 Windows 上使用 `shell: true`:

```typescript
// L271-279
const args = files.length > 0
  ? ['vitest', 'run', '--related', ...files]  // files 来自工具返回的文件路径
  : ['vitest', 'run'];
const result = spawnSync('npx', args, {
  cwd: projectPath,
  timeout: TEST_TIMEOUT,
  encoding: 'utf-8',
  shell: process.platform === 'win32',  // Windows 上 shell: true
});
```

如果工具返回恶意构造的文件路径（如 `foo.ts & del /s /q C:\`），在 shell 模式下会执行注入的命令。

**修复建议**:
```typescript
// Windows 上不使用 shell，直接调用 npx.cmd
const cmd = process.platform === 'win32' ? 'npx.cmd' : 'npx';
const result = spawnSync(cmd, args, {
  cwd: projectPath,
  timeout: TEST_TIMEOUT,
  encoding: 'utf-8',
  // 不设 shell: true
```

### I6: 安全检查黑名单可被绝对路径绕过

**文件**: [security.ts](file:///c:/Users/杨铭/Desktop/Agent/routedev/src/tools/security.ts#L363-L372)

**验证结果**: 已确认（降级自 Critical）⚠️

**描述**: 黑名单检查使用 `cmd.command.toLowerCase() === blParsed.command.toLowerCase()` 精确匹配首 token。如果黑名单有 `rm`，命令为 `/usr/bin/rm`，首 token 是 `/usr/bin/rm`，不匹配 `rm`，黑名单被绕过。

**缓解因素**: `checkBashSecurity` Layer 4 使用 `\brm\b` 正则匹配命令中的 `rm` 关键词，能捕获 `/usr/bin/rm -rf /` 等危险命令。但非危险命令（如 `curl`）的黑名单绕过仍有效。

**修复建议**: 黑名单匹配时提取命令 basename:
```typescript
const cmdBasename = path.basename(cmd.command.toLowerCase());
if (cmdBasename === blParsed.command.toLowerCase()) return true;
```

### I7: 速率限制仅 warn 不阻断

**文件**: [security.ts](file:///c:/Users/杨铭/Desktop/Agent/routedev/src/tools/security.ts#L495-L525)

**验证结果**: 已确认（降级自 Critical）⚠️

**描述**: `trackRateLimit` 方法在超限时仅 `logger.warn()`，不返回拒绝信号。`checkNetworkRequest` 调用 `this.trackRateLimit(hostname)` 后不检查任何返回值，速率限制形同虚设。

**缓解因素**: 速率限制是二级防御。主防御（SSRF 检查、网络白名单、HTTPS-only）仍有效。

**修复建议**: 让 `trackRateLimit` 返回 boolean，`checkNetworkRequest` 检查返回值并拒绝超限请求。

### I8: WebhookServer stop() Promise 可能永远挂起

**文件**: [server.ts](file:///c:/Users/杨铭/Desktop/Agent/routedev/src/channels/server.ts#L110-L121)

**验证结果**: 已确认 ✅

### I10: Worker 执行无超时保护

**文件**: [execution-orchestrator.ts](file:///c:/Users/杨铭/Desktop/Agent/routedev/src/agent/execution-orchestrator.ts#L484-L509)

**验证结果**: 逻辑分析确认 ✅

**描述**: `workerExecutor.execute()` 调用没有传入超时参数。如果 Worker 挂起（LLM API 不响应、工具死锁），整个并行组将永远阻塞。

**修复建议**: 为每个 Worker 添加独立 AbortController + 超时:
```typescript
const workerTimeout = this.deps.config?.execution?.workerTimeoutMs ?? 300_000;
const workerController = new AbortController();
const timer = setTimeout(() => workerController.abort(), workerTimeout);
try {
  return await workerExecutor.execute(task, ..., workerController.signal);
} finally {
  clearTimeout(timer);
}
```

## 架构层面建议

1. **统一并行/串行模式逻辑** — `loop.ts` 的 `run()` 方法约 900 行，并行/串行模式的工具执行逻辑高度重复（确认→中间件→策略引擎→钩子→执行→结果注入）。C1 安全漏洞正是这种重复导致的不对称。建议提取 `executeSingleToolCall()` 共用方法。

2. **completion-gate 异步化** — `spawnSync` 阻塞事件循环最长 120 秒，对面向用户的 Agent 系统不可接受。应改为异步 `spawn` + Promise。

3. **安全检查统一 basename 提取** — 黑名单/白名单匹配时应提取命令 basename 进行比较，防止绝对路径绕过。
