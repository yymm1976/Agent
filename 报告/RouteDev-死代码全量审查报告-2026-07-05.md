## 审查总结

RouteDev 经过 70+ Phase 的快速迭代，积累了大量实验性代码和配置门控子系统。本次审查通过 CodeGraph 静态调用图分析（5117 节点、11513 边），结合手动验证，系统识别出 **6 个完整死子系统（合计约 60+ 文件）**、**8 个未注册命令**、**14 条孤立 IPC 通道**、**2 个不可达页面**，以及 **5 处"实例化即丢弃"的无效装配代码**。死代码约占项目总量的 **15-20%**，建议分优先级清理。

## 做得好的地方

1. **app-init.ts 的 fail-open 动态导入模式**设计合理——对可选模块使用 `.catch(() => {})` 静默失败，保证了核心路径的稳定性。问题不在于这个模式本身，而在于太多模块停留在"可选但永远不启用"的状态。

2. **CommandRegistry 的注册表模式**清晰干净——42 个已注册命令都经过 `register()` 显式注册，死命令的边界（未注册 vs 已注册）非常明确，便于识别和清理。

3. **配置 schema 的 zod 验证**为每个配置项提供了 `default()` 值，使得配置门控模块的行为可预测——这也是为什么我们能明确判定哪些模块在默认配置下是死代码。

原报告过度依赖静态调用图的"零调用者"判定，未充分核验以下场景：
1. **动态 import()**：`app-init.ts` 大量使用 `import(path).then(mod => new mod.X())` 模式，CodeGraph 难以追踪
2. **配置门控实例化**：`if (config.X?.enabled) { new X(); }` 受配置守护的实例化在静态图中不可见
3. **跨入口点引用**：`src/cli/server.ts` 是独立入口（`routedev serve`），与主 CLI 入口 `App.tsx` 分离，原报告未充分覆盖
