# RouteDev 与基础 Pi 的能力差距分析

> 日期：2026-07-30  
> 对照对象：Pi 官方仓库当前实现、Pi Study 基于 Pi v0.82.0 的教学拆解  
> 结论口径：只把“基础 Pi 已经稳定具备、RouteDev 当前缺失或实现明显更弱”的部分列为差距；RouteDev 的扩展能力不因此被忽略。

## 1. 执行摘要

RouteDev 不是“功能比 Pi 少”的产品。它在模型路由、审批与安全策略、目标/检查点、审计追踪、桌面任务监控方面已经比基础 Pi 更重、更完整。真正的问题是：RouteDev 在 Agent 最基础的协议层和上下文链路上不够扎实，导致上层 UI 与高级功能建立在不稳定的语义之上。

确认存在的主要差距如下：

| 优先级 | 领域 | RouteDev 当前状态 | 基础 Pi 的基线 | 用户影响 |
|---|---|---|---|---|
| P0 | 事件与时间线协议 | 事件主要按 `thinking/text/tool_*` 分类，缺少完整的 agent/turn/message 生命周期；还会生成固定“模型思考中”文案 | 明确区分 agent、turn、message、tool 的 start/update/end，并按发生顺序发出 | 思考、进度、工具调用容易被错误聚合，时间顺序失真 |
| P0 | 可嵌入与远程控制 | 只有 Electron IPC，没有稳定的外部 RPC/HTTP/SSE 协议 | JSONL RPC 已覆盖发送、插话、排队、终止、会话树、压缩、重试和统计 | 安卓端、自动化和第三方客户端无法可靠接入 |
| P0 | 会话树 | 渲染层类型仍标注为占位/未来集成 | 会话树、分叉、克隆和游标是完整能力 | 长任务无法自然回溯、分支和恢复 |
| P1 | 项目上下文 | 项目规则/记忆能力存在，但此前主对话没有把它们送入系统提示词 | 项目上下文文件是系统提示词的正式组成部分 | 模型经常重复调查、忽视仓库约束 |
| P1 | Skill 渐进披露 | 关键词匹配后一次性注入多个 Skill 全文 | 启动时只给名称、描述、位置；命中后再读取正文和引用资源 | 浪费上下文，也可能因误匹配污染指令 |
| P1 | 工具面设计 | “核心工具不超过 10 个”的注释与实际默认注册约 19 个工具不一致，工具能力存在重叠 | 默认工具集小，系统提示词只展示当前可用工具 | 选择成本、提示词体积和误调用率偏高 |
| P1 | 性能评估 | 核心性能门禁主要基于零网络延迟的 mock LLM | Pi 的基础协议更容易做真实流式、事件和恢复测试 | 当前性能数字不能代表真实模型、Electron 或工具链 |
| P2 | 扩展抽象 | packs、plugins、hooks、middleware、skills、MCP 等入口较多且边界重叠 | 扩展与 Skill 的职责更聚焦 | 学习成本和维护成本高，故障定位慢 |

整体判断：RouteDev 的“能力上限”高于基础 Pi，但“基础闭环下限”低于 Pi。当前最重要的工作不是继续增加高级入口，而是先补齐事件协议、远程接口、会话语义和上下文披露。

## 2. 对照方法

本报告使用三类证据：

1. Pi 官方仓库中的系统提示词、Agent 事件类型、RPC 模式、Skill 加载逻辑。
2. Pi Study 对工具、循环、流式 UI、会话树、压缩、动态上下文、Skill、扩展、SDK/RPC 和桌面状态管理的章节拆解。
3. RouteDev 当前主对话调用链、工具注册、项目记忆、Skill 路由、会话树类型和性能门禁。

官方参考：

- Pi 源码：https://github.com/earendil-works/pi

## 3. 已确认比基础 Pi 更差的部分

### 3.1 事件协议不足，直接造成主对话时间线失真（P0）

RouteDev 的 `src/agent/loop-config.ts` 把事件分为思考、文本、工具开始/结果、审批、错误和完成等类别，但没有完整表达：

- 一次 Agent 执行何时开始和结束；
- 一个 turn 何时开始和结束；
- 一条 assistant message 的开始、增量更新和结束；
- 工具调用属于哪一条消息、哪一个 turn；
- 中途自然语言进度与工具调用之间的精确顺序。

更严重的是，`src/agent/loop.ts` 仍会发出类似“模型思考中……（模型，迭代 N）”的固定状态。这不是模型的真实输出，却被前端当成思考进度，正是此前页面出现“硬编码思考进度”的根因之一。

Pi 的基础事件类型明确提供：

- `agent_start` / `agent_end`
- `turn_start` / `turn_end`
- `message_start` / `message_update` / `message_end`
- `tool_execution_start` / `tool_execution_update` / `tool_execution_end`

这套语义让 UI 只需要按游标追加事件，就能自然呈现：

`模型文字 → 工具开始 → 工具结果 → 模型进度说明 → 下一个工具 → 最终回答`

而不需要先把“思考”“工具”“回答”分别收集，再猜测如何拼接。

**建议验收标准：**

- 每个事件拥有 `eventId`、`sessionId`、`turnId`、`messageId`、`sequence`、`timestamp`。
- 同一 turn 的 sequence 单调递增，重连后不重复也不丢失。
- 前端不生成任何伪模型文案；状态提示必须使用明确的 UI 标签，例如“正在等待模型”，不能伪装成模型消息。
- 历史重放与实时流使用同一事件结构。

### 3.2 缺少稳定的外部协议，无法自然扩展到安卓端（P0）

RouteDev 当前主进程和渲染层通过 Electron IPC 连接。这对单机桌面应用足够，但它不是可复用的 Agent 接口：

- 手机无法建立 IPC；
- 没有事件游标和断线续传；
- 没有设备身份、权限范围和撤销机制；
- 没有面向第三方客户端的版本化契约；
- 自动化工具不能稳定地 steer、follow-up、abort 或恢复会话。

Pi 的 JSONL RPC 已经把 Agent 的核心控制面暴露为协议，包括 prompt、steer、follow-up、abort、模型/思考等级、会话状态、压缩、重试、会话树、fork/clone 和统计信息。

RouteDev 的安卓计划不应绕过这一差距直接“遥控 UI”，而应先在桌面端建立版本化网关。详细实现见 `docs/plans/ANDROID_ROUTEDEV_REMOTE_GOAL_PLAN.md`。

### 3.3 会话树还是 UI 占位概念（P0）

`desktop/renderer/src/types/session-tree-types.ts` 明确把相关类型描述为占位和未来集成。基础 Pi 已经支持会话树、分叉、克隆和稳定游标。

这一差距不仅影响“高级用户功能”，也影响可靠性：

- 压缩前无法明确保留分支；
- 用户无法从失败步骤前恢复；
- 安卓端无法判断最新任务属于哪个分支；
- 工具审批后重放容易混入旧消息。

建议先定义引擎层 `SessionEntry` 和 `SessionBranch`，再由桌面和安卓共同消费，不要继续在渲染层单独造一套占位类型。

### 3.4 项目规则和项目记忆此前没有进入真实主链路（P1，已修）

RouteDev 已有 `loadProjectDoc` 和 `ProjectMemoryManager`，系统提示词模板也预留了项目规则与记忆，但主对话桥接此前没有传入这些值；`src/runtime/app-init-observability.ts` 甚至说明项目记忆消费者已经移除。

这意味着功能“看上去存在”，模型却收不到它。结果是：

- 重复读取已经确认的项目事实；
- 忽略 AGENTS.md 或项目规则；
- 压缩后丢失关键约束；
- 同类任务的行为不一致。

本轮已修复：

- 每轮对话从工作目录读取项目规则；
- 汇总 `.routedev` 项目记忆；
- 把两者作为独立高信号区块送入主系统提示词；
- 读取失败时安全降级为空，不把错误占位文本污染提示词。

涉及文件：

- `routedev/desktop/main/bridges/chat-bridge.ts`
- `routedev/src/prompts/manager.ts`
- 对应单元与集成测试

### 3.5 Skill 路由违背渐进披露原则（P1）

当前 `SkillsRouter` 主要依赖名称、描述和关键词的字符串命中，主对话最多自动选择多个 Skill，并把正文注入上下文。这有三个风险：

1. 相似词造成误命中；
2. 多个长 Skill 同时占用上下文；
3. Skill 内引用的资源没有统一的按需读取生命周期。

Pi 的基线更简单：启动上下文只给 Skill 名称、描述和位置，模型确认相关后再读取 `SKILL.md`；其中链接的参考资料继续按需加载。这与 Anthropic 的渐进披露建议一致。

建议：

- 系统提示词只注入 Skill 元数据；
- 提供一个统一的 `skill_read` 或文件读取入口；
- 记录“为什么选择这个 Skill”和加载了哪些资源；
- 只有用户显式指定时才强制加载正文；
- 用真实任务集评估 Skill 选择准确率，而不是只测试关键词。

### 3.6 默认工具过多且职责重叠（P1）

`src/runtime/app-init-tools.ts` 的注释要求核心工具不超过 10 个，但默认注册数量约为 19，包含基础工具、VFS 和 Plan 等多组工具。`src/tools/adapter.ts` 又把整个注册表的定义送给模型。

问题不在“19”这个绝对数字，而在于缺少按任务裁剪：

- 简单问答也看见不需要的写文件和计划工具；
- 文件读取可能同时存在多个抽象层；
- todo、plan、goal 的状态概念容易互相覆盖；
- 工具描述和系统提示词如果不一致，模型会按名称猜参数。

本轮已把真实工具描述加入系统提示词，而不是只列工具名；后续还需要根据任务形态生成活跃工具集。

建议将默认工具分为：

- 始终可见：4–6 个最小核心工具；
- 按工作区/任务激活：文件修改、计划、MCP、浏览器等；
- 显式授权后激活：高风险或外部副作用工具。

### 3.7 性能门禁不能代表真实 Harness 性能（P1）

`tests/integration/performance-benchmark.test.ts` 使用零网络延迟的 mock LLM，主要验证：

- 分类耗时；
- 简单端到端总时长；
- 堆内存；
- 初始化时间。

这能抓住明显的本地回归，但不能回答用户真正关心的问题：

- 首 token 多久出现；
- 工具开始前多花了多少编排时间；
- 真实模型流中是否丢事件或乱序；
- MCP 重连后能否恢复；
- 上下文压缩后关键约束保留率；
- 审批等待和审计写盘对 p95 延迟的影响；
- Electron 主线程是否卡顿。

因此当前性能门禁应定位为“本地烟雾测试”，不能作为 Harness 性能优秀的证据。完整指标设计见 Harness 系统评估报告。

### 3.8 扩展入口过多，边界不如基础 Pi 清楚（P2）

RouteDev 同时存在 packs、plugins、hooks、middleware、skills、MCP 等能力。每一项单独看都有价值，但它们在“注入上下文、增加工具、拦截调用、改变策略”上存在交叉。

基础 Pi 的扩展模型更容易解释：

- Skill 负责按需知识/工作流；
- Extension 负责代码级能力扩展；
- RPC/SDK 负责嵌入和外部控制。

建议 RouteDev 给每种扩展定义唯一职责和禁止事项，并统一生命周期、错误隔离、权限声明与可观察性。不需要立即删除功能，但要停止新增第七种入口。

## 4. RouteDev 明显优于基础 Pi 的部分

为避免“拿 Pi 当完整产品模板”，以下 RouteDev 优势应保留：

### 4.1 模型路由

RouteDev 已把模型选择、回退、任务路由放在更核心的位置，适合多模型工作台，而基础 Pi 更接近一个直接、可组合的 coding agent。

### 4.2 安全、审批和策略控制

RouteDev 对命令风险、审批、工具策略和审计的投入更大。这对桌面端和未来远程安卓端尤其重要。远程能力不能削弱现有桌面安全边界。

### 4.3 目标、检查点和任务监控

RouteDev 的 goal/checkpoint/任务监控适合长任务。需要改进的是状态语义统一，而不是退回到无结构对话。

### 4.4 可观察性

Trace collector、审计日志、工具统计为性能评估和故障复盘提供了良好基础。短板在于尚未形成真实 workload、端到端指标和一致事件协议。

### 4.5 桌面工作台

RouteDev 对任务、待办、产物、设置和模型管理的产品化目标高于基础 Pi。应继续走工作台路线，但底层事件协议需要先稳定。

## 5. 建议路线图

### P0：先修基础闭环

1. 定义版本化 Engine Event v1，替代松散的 UI 事件拼接。
2. 删除硬编码“模型思考中”模型文案；UI 状态和模型输出分离。
3. 把会话树、消息游标、工具调用关联移动到引擎公共类型。
4. 实现本地 Gateway：REST 命令 + SSE 事件 + Last-Event-ID。
5. 保证桌面 UI 和安卓 UI 都只消费同一事件流。

### P1：降低上下文和工具噪声

1. Skill 改为元数据优先、正文按需读取。
2. 工具按任务生成活跃集合，核心工具控制在 4–8 个。
3. 统一 todo/plan/goal：todo 是当前会话的可替换快照，goal 是跨轮次持久目标。
4. 建立真实模型与真实工具 workload 的性能基线。
5. 把同步审计写入改为有界异步队列并测试崩溃恢复。

### P2：收敛扩展体系

1. 为 plugin、pack、hook、middleware、skill、MCP 制定职责矩阵。
2. 合并重复的上下文注入和工具注册入口。
3. 对扩展设置 token、时间、权限和错误隔离预算。

## 6. 成功标准

当以下条件同时满足时，可以认为 RouteDev 的基础 Harness 不再弱于 Pi：

- 真实时间线中所有模型文字、工具调用、审批和结果严格按 sequence 展示；
- 断网重连后通过游标补齐事件，重复率和丢失率均为 0；
- 桌面和安卓对同一会话展示一致；
- 项目规则在压缩和恢复后仍能通过回归任务验证；
- Skill 正文只在相关任务中加载，平均 Skill 上下文 token 明显下降；
- 简单任务的活跃工具数不超过 8；
- 会话分叉、恢复和取消有端到端测试；
- 性能报告提供 p50/p95/p99，而不是只给 mock 总时长。
