# RouteDev Harness 系统性评估

> 日期：2026-07-30  
> 范围：上下文工程、Agent 循环、事件协议、工具设计、安全、可靠性、会话、可观察性、性能评测、扩展性、远程能力和成本  
> 总分：**5.9 / 10**

## 1. 一句话结论

RouteDev 已经拥有一个“高级功能很多”的 Harness，但还不是一个“基础语义非常稳”的 Harness。它的安全、路由、审计和长任务能力具有产品价值；上下文链路、事件时间线、工具裁剪、会话协议和真实评测则明显拖累整体表现。

总分 5.9 并不代表不可用，而代表结构失衡：强项接近 8 分，弱项只有 3–5 分。继续堆功能会放大这种失衡。

## 3. 评估原则

本报告不是按照“功能数量”打分，而是考察 Harness 是否能用最少、最相关的上下文和工具，可靠地完成任务，并让客户端准确观察和控制执行。

采用的基准思想：

1. **正确性优先于功能数量。**
2. **事件必须有可重放语义，而不只是给当前 UI 使用。**
3. **上下文是有限资源，应该按需加载。**
4. **工具应该最少、清楚、不重叠。**
5. **性能必须在真实流式模型、真实工具和真实客户端上测量。**
6. **安全边界在桌面、远程和自动模式中必须一致。**

参考方向包括 Pi 的基础 Agent/RPC 设计，以及 Anthropic 关于强模型时代上下文工程和 Skill 渐进披露的公开工程实践。

## 4. 分维度审查

### 4.1 上下文工程：4.5 / 10

#### 优点

- 已有 PromptManager，系统提示词不是散落字符串。
- 已有项目规则、项目记忆、Skill、压缩与任务形态等概念。
- 已能根据语言、自主模式和工作目录渲染提示词。
- 本轮已补上项目规则、项目记忆和工具描述的真实主链路。

#### 主要问题

1. **存在“组件已实现但消费者断开”的情况。**  
   `loadProjectDoc` 和 `ProjectMemoryManager` 已存在，但此前 `chat-bridge` 没有传入系统提示词。

2. **Skill 使用关键词自动匹配并注入正文。**  
   这不是严格的按需披露，可能同时带来 token 浪费和指令冲突。

3. **工具上下文此前只有名称。**  
   模型需要猜测工具用途；本轮已经改为名称加单行描述。

4. **没有上下文预算账本。**  
   项目规则、记忆、Skill、工具定义、历史消息和压缩摘要分别用了多少 token，目前难以观测。

5. **压缩后的事实保真缺少任务级评估。**  
   有压缩机制不等于关键约束能被准确保留。

#### 本轮改动

`main.system` 已重写为高层次、少分支、可执行的约束，包含：

- 身份与工作原则；
- 不同任务类型的执行边界；
- 工具选择、失败处理和权限边界；
- 项目规则与项目记忆；
- 当前会话 todo 替换规则；
- 真实进度与时间线要求；
- 完成条件和验证要求。

主对话桥接现在每轮读取最新项目规则和记忆，并提供真实工具描述。

#### 建议指标

- 每轮 prompt token 分项占比；
- 无关 Skill 加载率；
- 项目规则命中率；
- 压缩前后关键事实保留率；
- 相同任务在冷启动/压缩后/恢复后三种状态的成功率差；
- 工具描述 token 与正确选择率的关系。

### 4.2 Agent 循环与事件协议：5.0 / 10

#### 优点

- 已有迭代循环、工具调用、审批、错误、升级和完成事件。
- 流式生成与工具执行可以交替。
- 能支撑多模型和路由逻辑。

#### 主要问题

- 缺少 agent/turn/message 的标准 start/update/end 生命周期。
- 工具事件没有充分暴露其所属 message/turn 的公共关联键。
- 固定“模型思考中”文案与模型真实文字混淆。
- UI 容易按类别聚合，而不是按 sequence 追加。
- 事件历史与实时事件还不是一个统一、版本化的可重放协议。

#### 对产品的影响

这正是主页面“思考过程不合逻辑”“模型中间进度没有展示”“工具调用看上去插错位置”的底层原因。单纯修改 React 排版只能暂时遮盖问题。

#### 建议

建立 `EngineEventV1`：

- 公共字段：`id/sessionId/turnId/messageId/sequence/timestamp/type`；
- 消息：start/delta/end；
- 工具：start/progress/end；
- 审批：requested/resolved；
- todo：snapshot；
- artifact：published/replaced；
- runtime：status/error/done。

桌面 IPC、远程 SSE、历史存储和安卓端全部使用同一类型。

### 4.3 工具调用设计：5.5 / 10

#### 优点

- 工具注册表、适配器、审批和错误通路完整度较高。
- MCP manager 具备重连和安全治理能力。
- 有 todo、计划、文件、命令等适合 coding agent 的工具。

#### 主要问题

- 默认核心工具数量与代码注释的设计目标不一致。
- 多个文件/计划/任务抽象之间有重叠。
- 简单任务也可能暴露完整工具表。
- 工具失败后的重试和替代策略主要依赖提示词，没有统一的错误分类动作表。
- 自动模式失败曾被“命令含管道或命令替换需确认”拦截，说明自主模式、工具执行器与安全判定之间曾存在信息传递断点。

#### 建议

1. 引入 `ToolProfile`：answer、inspect、edit、build、remote 五档。
2. 简单任务默认只激活 4–8 个工具。
3. 合并同义工具或明确唯一使用场景。
4. 错误结果必须结构化：`code/retryable/requiresApproval/safeAlternative`。
5. 自动模式只跳过“可跳过的交互确认”，绝不能绕过命令黑名单、路径边界或运行时 `allowed=false`。

### 4.4 安全与权限：8.0 / 10

#### 优点

- 风险命令审批、工具权限和审计是 RouteDev 的真实优势。
- 自动模式没有被设计成无条件放行。
- 审批与错误事件可以被 UI 观察。
- 审计链为远程控制提供了良好基础。

#### 风险

- 自主模式曾与命令解析层不一致，导致本应自动执行的安全命令仍失败。
- 远程客户端会扩大攻击面：设备 token、重放、局域网暴露、跨设备审批都必须重新建模。
- 工具输出属于不可信输入，可能包含提示注入。

#### 安卓项目必须坚持

- 网关默认只监听 `127.0.0.1`；
- 外部访问交给 Tailscale Serve；
- 手机不保存模型供应商密钥；
- 设备 token 哈希存储、可撤销、有 scope；
- 高风险审批仍由桌面策略引擎作最终决定；
- SSE 只推送已授权会话；
- 所有远程命令进入审计日志。

### 4.5 可靠性与恢复：7.0 / 10

#### 优点

- 有重试、错误分类、检查点、goal 和 trace。
- 长任务恢复思路比轻量 Agent 更完整。
- MCP 有连接管理。

#### 短板

- 缺少统一事件游标，恢复后 UI 状态很难做到严格一致。
- 会话树未成为公共能力。
- todo、plan、goal 的生命周期边界不够清楚。
- 一些状态在 renderer 中二次推导，重启后可能无法重建。

#### 推荐不变量

- todo 是当前会话内的完整快照；新快照替换旧快照。
- goal 是明确创建的跨轮次目标，不能由普通任务自动推断。
- artifact 是独立实体，不作为 todo 子项重复展示。
- 所有 UI 状态都能从持久化 EngineEvent + 当前实体快照重建。

### 4.6 会话连续性：5.0 / 10

#### 现状

RouteDev 具备历史、压缩、项目记忆和目标等能力，但缺少一个统一的会话模型把它们连接起来。会话树类型仍是渲染层占位。

#### 建议模型

- `Session`：一个用户可见任务；
- `Branch`：从某个 entry 分叉的执行路径；
- `Turn`：一次用户输入到 agent 稳定结束；
- `Message`：用户、assistant 或 tool 的内容实体；
- `Event`：上述实体的时间序列变化；
- `TodoSnapshot`：当前 turn/会话的任务快照；
- `Artifact`：独立产物；
- `GoalRef`：可选的跨会话目标引用。

### 4.7 可观察性：7.5 / 10

#### 优点

- Trace collector 有批处理、背压和低优先级丢弃策略。
- 审计日志默认启用。
- 已有性能门禁入口，说明团队重视回归。

#### 问题

- 审计路径中逐条同步写盘可能造成主线程抖动。
- trace 指标与用户可感知指标没有统一关联 ID。
- 没有“从用户发送到首 token、首工具、最终完成”的标准 span。
- 事件丢弃策略需要明确哪些类型绝不能丢。

#### 建议

- 为每个 turn 建 root span；
- 记录 routing、prompt build、provider wait、decode、tool queue、tool run、approval wait、persistence；
- 审计改为有界异步队列，关键记录支持 flush；
- `message_delta` 可降采样，start/end/error/approval/todo/artifact 绝不能丢；
- 桌面状态栏的数据必须来自同一 telemetry schema。

### 4.8 评测与性能基准：3.5 / 10

#### 当前门禁能证明什么

- 本地函数没有出现数量级退化；
- mock 条件下初始化、分类和简单循环在阈值内；
- 基础堆内存没有明显泄漏。

#### 当前门禁不能证明什么

- 真实供应商首 token 和吞吐；
- Electron renderer/main 的卡顿；
- 工具并发、审批、MCP 网络和审计写盘；
- 长上下文与压缩；
- 断线恢复和事件一致性；
- 任务成功率与代码质量。

#### 推荐基准矩阵

| 场景 | 样本 | 核心指标 |
|---|---|---|
| 简单问答 | 20 个稳定问题 | TTFT、总时长、prompt token |
| 仓库调查 | 10 个符号/调用链任务 | 工具次数、无关读取、正确率 |
| 小型修复 | 10 个带测试 bug | 成功率、首次通过率、总成本 |
| 长任务 | 5 个 20+ 工具任务 | 压缩次数、事实保留、恢复成功率 |
| MCP | 3 类服务 × 故障注入 | 重连时长、重复调用、错误恢复 |
| 审批 | 自动/半自动/手动 | 误拦截率、漏拦截率、等待时间 |
| 事件流 | 乱序/断线/重连 | 丢失、重复、顺序错误 |
| 桌面 UI | 真实流式回放 | FPS、主线程长任务、内存 |
| 安卓远程 | Wi-Fi/Tailnet/切网 | 重连、通知延迟、电量 |

每项输出 p50/p95/p99 和失败样本，不只输出平均值。

#### 建议性能预算

- 本地网关命令确认：p95 < 150 ms；
- 事件进入桌面 UI：p95 < 50 ms；
- Tailnet 事件进入安卓 UI：p95 < 500 ms；
- 断线后恢复：p95 < 3 s；
- 已确认事件丢失率：0；
- 审计写入不造成 >50 ms 主线程长任务；
- Prompt 构建本地开销：p95 < 50 ms；
- 简单任务活跃工具定义 token 相比当前基线降低至少 40%。

### 4.9 扩展性：6.5 / 10

RouteDev 的扩展面很广，但“能扩展”不等于“容易可靠扩展”。

建议制定如下职责：

| 机制 | 唯一职责 |
|---|---|
| Skill | 按需知识、约束和工作流，不直接拥有常驻运行时 |
| MCP | 外部工具与资源协议 |
| Plugin | 可安装的产品能力包，声明权限和依赖 |
| Hook/Middleware | 内部生命周期拦截，只用于横切逻辑 |
| Pack | 若保留，仅作为配置分发单元，不再创造运行时语义 |

所有扩展统一声明：

- token 预算；
- 工具权限；
- 网络/文件权限；
- 超时；
- 错误隔离；
- telemetry 标签；
- 可卸载与版本兼容。

### 4.10 嵌入与远程能力：3.0 / 10

这是当前最明显的产品结构缺口。Electron IPC 适合内部进程，不适合作为产品协议。

安卓项目所需的最小公共面：

- 会话列表/详情；
- 创建会话、发送消息；
- steer、follow-up、abort；
- 事件 SSE 与游标恢复；
- todo/artifact 快照；
- Skill/MCP 列表与选择；
- 审批读取与决策；
- 设备配对、scope、撤销；
- 健康状态和协议版本。

该能力也会反向改善桌面端：只要桌面 UI 也使用同一 EngineEvent 语义，历史回放、测试和调试都会更简单。

### 4.11 成本与延迟控制：5.5 / 10

#### 有利条件

- 多模型路由可按任务选择成本/能力。
- 有压缩和项目记忆。
- Trace 可扩展为 token 与成本账本。

#### 当前损耗

- 自动注入多个 Skill 正文；
- 默认工具表偏大；
- 项目上下文没有明确大小上限和优先级；
- 扩展机制可能重复注入相同信息；
- 失败重试缺少全局 token/时间预算。

#### 建议

为每个 turn 建立预算：

- 系统固定区；
- 项目规则；
-项目记忆；
- Skill；
- 工具定义；
- 会话历史；
- 预留输出；
- 重试额度。

超预算时按优先级裁剪，而不是只依赖统一截断。

## 5. 与相似产品设计的对比

### 5.1 与 Pi

Pi 的优势是基础协议小而完整：事件、循环、Skill 渐进披露、会话树、RPC/SDK 都能组合。RouteDev 的优势是产品治理：路由、安全、审计、目标和桌面工作台更丰富。

RouteDev 应学习 Pi 的“基础能力可组合”，不需要复制 Pi 的极简产品定位。

### 5.2 与强模型时代的 Claude/Anthropic 方法

Anthropic 的公开建议强调：

- 系统提示词保持正确抽象层级；
- 给模型最小但充分的高信号上下文；
- 工具少而清晰，避免重叠；
- 信息即时检索，而不是全部预加载；
- 用压缩、结构化记忆和独立上下文管理长任务。

RouteDev 当前最偏离这些原则的地方是 Skill 全文自动注入、工具表偏大、项目上下文链路曾断开，以及缺乏 token 分项观测。

本轮系统提示词重写已朝这个方向调整：删掉特定 Phase 和临时流程痕迹，保留稳定行为约束，把运行时权限作为最终权威，并强调实际模型进度按时间顺序展示。

### 5.3 与 Codex 式工作台

Codex 类工作台给用户的核心感受不是“卡片更多”，而是：

- 模型中间说明与工具事件自然交错；
- 当前任务状态清楚；
- 输入区稳定、信息密度均衡；
- 产物、todo 和会话历史各自只有一个权威位置；
- 工具失败有清楚原因和可执行下一步。

因此 RouteDev 的前端美化应建立在 EngineEvent 和状态实体收敛之后。否则继续调字体、间距和卡片仍会被混乱数据模型拖累。

## 6. 已完成的本轮优化

### 系统提示词

修改 `routedev/src/prompts/manager.ts`：

- 使用“正确抽象层级”，减少脆弱的特例；
- 明确回答、调查、审查、诊断、修改、构建的授权边界；
- 强制最小相关上下文与工具；
- 工具失败先理解原因，不盲目重试；
- 工具输出视为不可信数据；
- 项目规则和项目记忆进入正式上下文；
- todo 是当前会话内的完整可替换快照；
- 进度必须来自模型真实输出，按时间线与工具事件交错；
- 完成前必须进行与风险相称的验证。

### 主对话上下文链路

修改 `routedev/desktop/main/bridges/chat-bridge.ts`：

- 每轮读取最新项目规则；
- 汇总项目记忆；
- 传入系统提示词；
- 工具从“只有名称”升级为“名称 + 一行描述”；
- 文件缺失或读取失败时安全降级。

### 回归测试

修改：

- `routedev/tests/prompts/manager.test.ts`
- `routedev/desktop/main/__tests__/chat-bridge.integration.test.ts`

覆盖项目规则、项目记忆、工具描述和旧临时提示词痕迹的回归。

## 7. 90 天建议路线

### 0–2 周：稳定协议

- EngineEvent v1；
- 删除伪思考文案；
- todo/artifact 单一权威状态；

## 8. 最终判断

RouteDev 现在最应该追求的不是“比 Pi 更多”，而是“先做到 Pi 那样基础清晰，再保留自己的高级治理优势”。

如果只完成三件事，应按以下顺序：

1. 统一事件与会话协议；
2. 建立可恢复的本地远程网关；
3. 让 Skill、工具和项目上下文真正按需、可测、可预算。

完成后，RouteDev 的桌面 UI、安卓端、性能测试和系统提示词会共享同一套基础语义，后续迭代成本会显著下降。
